# AI_helper

Личный ИИ-ассистент в Telegram: отвечает на сообщения, помнит контекст разговора,
позже научится понимать голос и ставить напоминания. Отвечает только владельцу.

Проект собирается с нуля, по шагам — каждый шаг доводится до рабочего состояния,
прежде чем начинается следующий. Этот файл — заодно и журнал: что сделано, какими
командами и почему именно так.

## Быстрый старт

Нужен Python 3.12 и токен Telegram-бота от [@BotFather](https://t.me/BotFather).

```powershell
# 1. Виртуальное окружение (Windows)
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# 2. Зависимости
pip install -r requirements.txt

# 3. Конфигурация
copy .env.example .env
#    Заполнить BOT_TOKEN, ALLOWED_USER_IDS, GROQ_API_KEY

# 4. Запуск
python -m app.bot
```

На Linux/macOS отличаются только две строки: `source .venv/bin/activate` и `cp .env.example .env`.

Запускать нужно **модулем** (`python -m app.bot`), а не файлом (`python app/bot.py`) —
иначе Python не найдёт пакет `app` и импорты вида `from app.config import ...` упадут.

Если окружение не активировано, можно вызвать интерпретатор напрямую:

```powershell
& .\.venv\Scripts\python.exe -m app.bot
```

Остановка — `Ctrl+C`.

### Свой Telegram ID

Нужен для `ALLOWED_USER_IDS`: напиши что угодно боту [@userinfobot](https://t.me/userinfobot),
он ответит числовым идентификатором.

## Запуск в Docker

Так бот работает на сервере: поднимается сам после перезагрузки, переживает
падения, не зависит от твоего компьютера.

```bash
docker compose up -d --build    # собрать и запустить в фоне
docker compose logs -f          # смотреть логи
docker compose restart          # перезапустить
docker compose down             # остановить и удалить контейнер
```

Обновление после правки кода — те же полминуты:

```bash
git pull
docker compose up -d --build
```

**Одновременно можно запускать только одну копию бота.** Telegram разрешает
long polling лишь одному процессу на токен: если локальный бот запущен, контейнер
будет драться с ним за апдейты, и оба начнут получать ошибку `Conflict`.
Перед `docker compose up` останови локальный запуск.

### Развёртывание на сервере

```bash
git clone <репозиторий> && cd AI_helper
cp .env.example .env && nano .env        # вписать токен и ключи

# Папка данных должна принадлежать пользователю 1000 — под ним работает
# процесс внутри контейнера. Без этого бот не сможет создать файл базы.
mkdir -p data && sudo chown 1000:1000 data

docker compose up -d --build
```

Проверить, что живой: `docker compose logs -f` — должна появиться строка
`Бот @… запущен` и следом `Планировщик запущен`.

### Резервная копия

Всё состояние — один файл. Копировать можно на ходу, останавливать бота не нужно:

```bash
sqlite3 data/assistant.db ".backup data/backup.db"
```

## Команды бота

| Команда | Что делает |
|---------|-----------|
| `/start` | приветствие и краткая справка |
| `/new` | начать разговор с чистого листа, забыв контекст |
| `/reminders` | список активных напоминаний напрямую из базы, без обращения к модели |
| `/status` | какие модели используются, сколько реплик в памяти, когда протухнет диалог |
| любой текст | обычный вопрос к ассистенту или просьба поставить напоминание |
| голосовое | распознаётся в текст и обрабатывается так же, как обычный вопрос |

Напоминания ставятся обычной фразой — «напомни завтра в 9 позвонить маме»,
«не забыть бы в пятницу забрать посылку». Отдельной команды для этого нет:
модель сама решает, разговор перед ней или просьба о действии.

Повторяющиеся — так же: «напоминай каждый день в 9 выпить таблетки», «по будням
в 7:30 про зарядку», «первого числа каждого месяца оплатить интернет»,
«каждые полчаса размять глаза». Отмена повторяющегося прекращает всю серию.

## Настройки (`.env`)

| Переменная | Обязательна | Назначение |
|------------|-------------|-----------|
| `BOT_TOKEN` | да | токен бота от @BotFather |
| `ALLOWED_USER_IDS` | да | белый список ID через запятую |
| `GROQ_API_KEY` | да | ключ [console.groq.com](https://console.groq.com/keys) |
| `TZ` | нет | часовой пояс IANA, по умолчанию `UTC` |
| `LLM_BASE_URL` | нет | адрес API, по умолчанию Groq |
| `LLM_MODEL` | нет | модель, по умолчанию `openai/gpt-oss-120b` |
| `LLM_TEMPERATURE` | нет | разброс ответов, по умолчанию `0.4` |
| `LLM_TIMEOUT_SECONDS` | нет | ожидание ответа модели, по умолчанию `60` |
| `STT_MODEL` | нет | модель распознавания речи, по умолчанию `whisper-large-v3-turbo` |
| `STT_LANGUAGE` | нет | язык голосовых, по умолчанию `ru`; пусто — автоопределение |
| `MAX_VOICE_SECONDS` | нет | предел длительности голосового, по умолчанию `300` |
| `REMINDER_TICK_SECONDS` | нет | период опроса базы планировщиком, по умолчанию `30` |
| `MISSED_REMINDER_GRACE_DAYS` | нет | до скольких дней опоздания напоминание ещё шлётся, по умолчанию `7` |
| `MAX_TOOL_ROUNDS` | нет | предел вызовов инструментов на одно сообщение, по умолчанию `5` |
| `SESSION_TTL_MINUTES` | нет | простой до конца диалога, по умолчанию `120` |
| `MAX_HISTORY_MESSAGES` | нет | сколько реплик уходит в модель, по умолчанию `20` |

Файл `.env` в репозиторий не попадает. Шаблон со всеми переменными — `.env.example`.

## Как устроено

```
app/
├── config.py     чтение и проверка .env — единственное место, знающее про переменные окружения
├── access.py     белый список: посторонние отсекаются до всякой логики
├── api_errors.py перевод ошибок провайдера в понятные пользователю фразы
├── prompts.py    системный промпт с текущей датой и днём недели
├── history.py    диалоги: сессии, протухание по бездействию, обрезка контекста
├── llm.py        клиент к модели — единственное место, знающее про Groq
├── stt.py        распознавание речи (Whisper на том же ключе)
├── db.py         подключение к SQLite и схема
├── recurrence.py правила повторения и расчёт следующего срабатывания
├── reminders.py  хранение напоминаний и планировщик отправки
├── tools.py      описания инструментов для модели и их исполнение
├── agent.py      цикл «модель просит — выполняем — модель формулирует ответ»
└── bot.py        обработчики Telegram, точка входа
```

Путь одного сообщения:

```
Telegram
   ↓
WhitelistMiddleware      чужой ID → молча отбрасываем
   ↓
handle_text              ┐
handle_voice → stt.py    ┘ голосовое распознаётся и дальше идёт как текст
   ↓
reply_with_llm           берём замок на пользователя
   ↓
HistoryStore             активная сессия (или новая, если прошлая протухла)
   ↓                     + последние N реплик
agent.respond            системный промпт + история + описания инструментов → Groq
   ↓                     модель просит вызов → ToolBox выполняет → результат обратно
   ↓                     (до MAX_TOOL_ROUNDS кругов)
ответ                    режем на части по 4000 символов, отправляем
   ↓
HistoryStore             сохраняем реплику пользователя и финальный ответ
```

Напоминание живёт отдельно от разговора:

```
ToolBox.create_reminder → SQLite (data/assistant.db)
                              ↑
ReminderScheduler ───────────┘   раз в 30 секунд: «что уже пора?»
   ↓
bot.send_message                 бот пишет сам, без входящего сообщения
```

## Принятые решения и почему

### Белый список — middleware, а не проверка в каждом обработчике

Прослойка стоит на уровне апдейта и срабатывает раньше, чем подбирается обработчик.
Правило описано один раз и автоматически распространяется на всё, что добавится
дальше — голосовые, кнопки, команды. Забыть про проверку в новом обработчике
физически невозможно.

Посторонним бот не отвечает вообще ничего. Сообщение вида «у вас нет доступа»
подтверждало бы, что бот жив, и провоцировало продолжать.

### Конфигурация падает на старте

`config.py` при импорте проверяет всё: обязательные переменные на месте,
ID числовые, часовой пояс существует. Лучше не запуститься с внятной ошибкой,
чем работать и сломаться через неделю в момент срабатывания напоминания.

### Провайдер модели изолирован в одном файле

`llm.py` — единственное место, знающее про Groq. Наружу торчит «дай историю —
получи ответ». Groq говорит на протоколе OpenAI, поэтому используется библиотека
`openai`: смена провайдера на OpenRouter, локальную модель или сам OpenAI — это
правка `LLM_BASE_URL` и `LLM_MODEL` в `.env`, без единой строки кода.

Бесплатные лимиты меняются, и не хочется быть привязанным к одному поставщику.

### Ответ модели описан как «текст ИЛИ вызов инструментов»

Инструментов пока нет, но тип ответа уже предусматривает их. На шаге с
напоминаниями останется описать функцию и передать её в `complete()` — логика
бота не изменится.

Почему вообще инструменты, а не поиск ключевых слов: фраза «не забыть бы завтра
позвонить маме» слова «напомни» не содержит, а напоминание нужно. И наоборот,
«напомни, как работает GROUP BY» — это вопрос, а не будильник. Различить их
можно только по смыслу, и это работа модели, а не регулярного выражения.

### Голос — это просто ещё один способ ввода

Голосовое распознаётся в текст и передаётся в ту же функцию, что и набранное
руками (`reply_with_llm`). Никакой отдельной «голосовой логики» нет: контекст,
сессии, обработка ошибок работают одинаково. Поэтому шаг с голосом занял один
небольшой модуль, а не переписывание бота.

Перекодировать аудио не нужно: Telegram отдаёт голосовые в OGG/Opus, а Groq
принимает этот формат напрямую — `ffmpeg` в зависимостях не появился.

Файл качается в память, а не на диск: голосовые небольшие, а временные файлы
пришлось бы удалять и думать о правах внутри контейнера.

Распознанный текст бот присылает отдельным сообщением с меткой 🎤. Whisper
иногда ошибается, и лучше сразу видеть, что именно бот услышал, чем гадать,
почему ответ не по теме.

Слишком короткие (меньше секунды) и слишком длинные записи отсекаются до
загрузки в API — провайдер на них всё равно вернёт ошибку, а лимит израсходуется.

### Диалоги протухают по бездействию

Утренний вопрос про историю Москвы и вечерний про SQL — разные разговоры.
Если складывать их в одну историю, модель начнёт притягивать неуместный контекст,
а лишние реплики будут съедать лимиты.

Механизм: при каждом сообщении сравнивается время последней активности с
`SESSION_TTL_MINUTES`. Фоновый таймер не нужен — пока пользователь молчит,
состояние никого не интересует.

Когда диалог начинается заново после простоя, бот помечает это строкой
`— новый диалог —`. Без пометки пользователь спросил бы «а подробнее?» и получил
«о чём речь?», решив, что бот сломался. При первом обращении и после ручного
`/new` пометки нет — там и так всё понятно.

### Планировщик — свой цикл, а не библиотека

Фоновая задача раз в `REMINDER_TICK_SECONDS` спрашивает у базы «что уже пора»
и отправляет найденное. Готовые планировщики (APScheduler и подобные) держат
собственный список задач, который надо синхронизировать с нашей таблицей —
это два источника правды, которые рано или поздно разъедутся.

Здесь источник один: база. Переживание перезапуска получается бесплатно —
бот поднялся, заглянул в таблицу, увидел просроченное. Цена — точность порядка
интервала опроса, что для напоминаний несущественно, и минус одна зависимость.

### Повторения — ограниченный набор правил, а не RRULE или cron

Поддерживаются четыре вида: каждый день, по указанным дням недели, раз в месяц
в определённое число и через равные промежутки времени. Полноценные календарные
правила (RRULE) или cron-строки дали бы больше свободы ценой чужой библиотеки
и краевых случаев вроде «пятая пятница месяца».

Узкий набор ещё и надёжнее в связке с моделью: чем меньше пространство
возможных значений, тем меньше ей есть где ошибиться, и тем полнее мы можем
проверить то, что она прислала.

Разовые и повторяющиеся напоминания — два разных инструмента
(`create_reminder` и `create_recurring_reminder`), а не один с флагом. Модели
проще выбрать из двух ясных описаний, чем правильно заполнить необязательные
поля, и на тестах она ни разу их не перепутала.

Для повторяющегося `fire_at` хранит ближайшее срабатывание и сдвигается вперёд
после каждой отправки. Отдельной таблицы «истории срабатываний» нет — она
никому не нужна.

Число месяца подгоняется под его длину: «31 числа» в феврале означает 28-е или
29-е. Пользователь, говоря «31 числа», обычно имеет в виду «в конце месяца»,
а не «пропускать короткие месяцы».

### Пропущенные напоминания приходят, но не любые

Если бот был выключен, просроченные напоминания уходят сразу при запуске,
с пометкой «должно было сработать в …» — без пояснения это выглядело бы сбоем.
Но только если опоздание меньше `MISSED_REMINDER_GRACE_DAYS`: напоминание
недельной давности уже не помогает, а сбивает с толку. Такие тихо помечаются
статусом `expired`.

С повторяющимися тоньше: серия не умирает от простоя, а следующее срабатывание
считается от «сейчас», а не от пропущенного времени. Если бот лежал месяц,
придёт одно напоминание, а не тридцать подряд за каждый пропущенный день.

### Схема доводится через ALTER TABLE

`CREATE TABLE IF NOT EXISTS` не трогает уже созданную таблицу, поэтому новые
колонки к существующей базе добавляются отдельно — `_ensure_column` в `db.py`
смотрит `PRAGMA table_info` и при необходимости выполняет `ALTER TABLE`.
Так колонка `repeat_rule` появилась в базе, созданной до повторяющихся
напоминаний, без потери данных и без ручных действий.

Полноценная система миграций (Alembic и подобные) для одного файла и одного
пользователя избыточна.

### Время в базе — всегда UTC

Модель возвращает время со смещением (`2026-07-28T09:00:00+03:00`), мы переводим
в UTC и храним так. К часовому поясу пользователя приводим только при показе.
Сервер после этого может стоять где угодно.

Если модель забыла указать смещение, время считается местным — так интуитивно
правильнее, чем принять его за UTC и ошибиться на несколько часов.

### Аргументы модели проверяются перед выполнением

Время в прошлом, нераспарсиваемая строка, пустой текст, выдуманный номер
напоминания, несуществующий инструмент — всё это отбивается, и модели
возвращается текст ошибки. Она исправляется сама: это штатный путь, а не аварийный.

Запросы к базе всегда содержат `user_id` — не паранойя, а защита от того, что
модель подставит номер из прошлого разговора или просто выдумает его.

### SQLite синхронный, и это осознанно

`sqlite3` блокирующий, а бот асинхронный. Формально это грех, практически —
запрос к локальному файлу при одном пользователе занимает доли миллисекунды.
Если упрёмся, `aiosqlite` заменит его в одном модуле (`db.py`).

Устанавливать SQLite не нужно: это библиотека внутри Python, а база — просто
файл `data/assistant.db`, который создаётся при первом запуске.

### История диалогов остаётся в памяти

Диалоги живут в памяти процесса и теряются при перезапуске — и так и останется.
Ассистент используется для коротких «вопрос-ответ», а не для долгих обсуждений,
поэтому терять там нечего. Напоминания при этом в базе: они обязаны переживать
перезапуск, а разговор — нет.

### Контекст обрезается, история хранится целиком

В модель уходят последние `MAX_HISTORY_MESSAGES` реплик, но в самой сессии
остаётся всё. Так позже можно будет складывать старые разговоры в архив и искать
по ним, ничего не переписывая.

### Замок на пользователя

aiogram обрабатывает апдейты параллельно. Два быстро отправленных сообщения
полезли бы в одну историю одновременно и перемешали реплики. Пока обрабатывается
одно сообщение, следующее ждёт.

### Реплики сохраняются только после успешного ответа

Если модель вернула ошибку, сообщение пользователя в историю не попадает. Иначе
там осталась бы висящая реплика без ответа, а повторная отправка создала бы дубль.

### Секреты не попадают в образ

`.env` исключён через `.dockerignore`, а переменные передаются при запуске
(`env_file` в `docker-compose.yml`). Вшитые в образ секреты уезжают вместе с
ним — образ можно выгрузить, переслать, залить в реестр. Разделение простое:
образ это код, `.env` это доступы.

### Данные живут в подключённой папке, а не в образе

Файловая система контейнера уничтожается при каждой пересборке. Строка
`./data:/app/data` в `docker-compose.yml` — единственное, что отделяет
«обновил бота» от «потерял все напоминания».

Побочная выгода: база остаётся обычным файлом на хосте, её можно копировать
и открывать любым просмотрщиком SQLite, не залезая в контейнер.

### Внутри контейнера бот работает не от root

Создаётся пользователь `appuser` с UID 1000. Если в боте когда-нибудь найдётся
уязвимость, у нападающего не будет прав администратора даже внутри контейнера.

Отсюда единственное требование к серверу: подключённая папка `data` должна
принадлежать UID 1000, иначе процесс не сможет создать в ней файл базы.
На Windows с Docker Desktop это не проявляется — там права отображаются иначе.

### Образ на python:3.12-slim, а не alpine

В alpine другая системная библиотека (musl), под которую нет готовых сборок
многих пакетов — они компилируются из исходников, превращая минутную сборку
в десятиминутную. Экономия размера того не стоит.

Зависимости ставятся до копирования кода: Docker кэширует слои по содержимому,
поэтому правка кода не тянет установку aiogram заново.

### Портов нет

Бот сам стучится в Telegram (long polling), входящих соединений не принимает.
Открывать порты незачем — на сервере это лишняя дверь.

Ротация логов ограничена тремя файлами по 10 МБ: по умолчанию Docker пишет
их без предела и со временем забивает диск.

### Разработка на Windows, запуск в Linux

Код пишется на Windows, боевой запуск планируется в Docker на Linux-сервере.
Что из этого следует:

* `.gitattributes` заставляет Git хранить переносы строк в Unix-формате — иначе
  скрипты внутри контейнера падают с `bad interpreter`;
* пути только через `pathlib`, никаких `C:\`;
* всё время внутри — в UTC, к часовому поясу приводится только на границах;
* пакет `tzdata` в зависимостях: в Windows системной базы часовых поясов нет
  вообще, в минимальных Linux-образах её обычно тоже нет.

Проверено на живом контейнере: системное время внутри — UTC, а `Europe/Moscow`
из `.env` применяется корректно (16:40 UTC → 19:40 по Москве).

Приятный побочный эффект: переменная `TZ` — стандартная для Linux, поэтому её
подхватывает и сам контейнер. Отметки времени в `docker compose logs` идут
по московскому времени, а не по UTC, — читать логи заметно удобнее.

### Ответы отправляются простым текстом

Модели в системном промпте запрещено использовать Markdown. Telegram умеет
размечать текст, но модель регулярно выдаёт разметку с ошибками, и тогда
отправка сообщения падает целиком. Читаемость `**жирного**` в чате — приемлемая
цена за то, что ответ дойдёт всегда.

## Находки и грабли

Собрано по ходу работы — всё проверено на этом проекте.

**Cloudflare перед Groq банит «безымянные» HTTP-клиенты.** Запрос через `urllib`
получает `HTTP 403, error code: 1010` — при полностью валидном ключе. Библиотека
`openai` проходит нормально. Если увидишь 1010, проверяй `User-Agent`, а не ключ.

**Модели плохо считают дни недели.** С промптом «сегодня 2026-07-27»
`gpt-oss-120b` ошиблась на два дня, вычисляя «в пятницу». После добавления в
промпт названия дня («понедельник, 27 июля 2026») обе проверенные модели считают
даты верно. Поэтому `prompts.py` подставляет день недели явно.

**Описание инструмента должно запрещать ложные срабатывания.**
`llama-3.3-70b-versatile` ставила напоминание в ответ на вопрос «напомни, как
работает GROUP BY», пока в описание функции не добавили «НЕ использовать, если
пользователь задаёт вопрос».

**Сравнение моделей на Groq** (4 сценария: обычный вопрос, явная просьба,
неявная просьба, вопрос-ловушка):

| Модель | Результат |
|--------|-----------|
| `openai/gpt-oss-120b` | 3/4 — ошиблась только в дате дня недели |
| `llama-3.3-70b-versatile` | 3/4 — даты считает верно, но попалась в ловушку |

После доработки промпта обе дают 3/3. Основной выбрана `gpt-oss-120b`: лишнее
напоминание раздражает сильнее, чем сдвиг даты, который виден в подтверждении.

**В Windows `python.exe` из `WindowsApps` — заглушка Microsoft Store**, а не
интерпретатор. Настоящий Python ищи в реестре:
`HKLM:\SOFTWARE\Python\PythonCore\*\InstallPath`.

**`ZoneInfo("Europe/Moscow")` падает без пакета `tzdata`.** В Windows системной
базы часовых поясов нет вообще, в минимальных Linux-образах её обычно тоже нет.
Пакет кладёт базу прямо в окружение и решает проблему в обеих средах сразу.

**Пробел в возможностях выглядит как странное поведение модели.** Самый
поучительный случай проекта. На просьбу «напоминай каждые полчаса» бот создал
пять разовых напоминаний подряд и оборвался на предохранителе `MAX_TOOL_ROUNDS`.

Причина была не в модели: интервальных повторений в наборе правил тогда просто
не существовало. Модель не говорит «я не умею» — она выкручивается доступными
инструментами, и получается разовое напоминание на 19:30, на 20:00, на 20:30…

Отсюда два вывода. Первый: когда бот ведёт себя нелепо, сначала проверь, есть ли
у него вообще подходящий инструмент. Второй: поднимать `MAX_TOOL_ROUNDS` в такой
ситуации бесполезно и вредно — вместо пяти мусорных записей получится девятнадцать.
Предохранитель показывает симптом, а не причину.

Лечится это двумя правками: добавить недостающую возможность и явно запретить
её имитацию в описании инструмента («НИКОГДА не вызывай этот инструмент
несколько раз подряд, чтобы изобразить повторяющееся напоминание»).

**Модель иногда всё же пробивается на разметку.** Запрет Markdown в системном
промпте соблюдается не идеально: обратные кавычки вокруг терминов вроде
`GROUP BY` проскакивают. На отправку это не влияет — сообщение уходит простым
текстом, просто с лишними символами.

**Проверить распознавание речи можно без микрофона.** Windows синтезирует речь
встроенными средствами, и полученный файл годится как тестовый:

```powershell
Add-Type -AssemblyName System.Speech
$s = New-Object System.Speech.Synthesis.SpeechSynthesizer
$s.SelectVoice('Microsoft Irina Desktop')   # список: $s.GetInstalledVoices()
$s.SetOutputToWaveFile('voice.wav')
$s.Speak('Привет! Расскажи, чем полезен индекс в базе данных.')
$s.Dispose()
```

На таком файле Whisper дал дословную расшифровку.

## Что доступно на Groq

Полезное из списка моделей на бесплатном ключе:

| Модель | Назначение |
|--------|-----------|
| `openai/gpt-oss-120b` | основная модель диалога |
| `llama-3.3-70b-versatile` | запасная |
| `llama-3.1-8b-instant` | быстрая и слабая, для простых задач |
| `whisper-large-v3`, `whisper-large-v3-turbo` | распознавание речи — шаг 3 |
| `groq/compound` | модель со встроенным веб-поиском |
| `canopylabs/orpheus-*` | синтез речи, если захочется голосовых ответов |

Распознавание речи доступно на том же ключе и тарифе, что и чат, — отдельный
провайдер для голосовых не понадобится.
